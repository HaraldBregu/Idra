# The Anatomy of an AI Agent Harness: A Layered Architecture Reference for Diagramming

## TL;DR
- An agent harness is **everything that wraps a stateless LLM to make it a functional agent** — the canonical formula is **"Agent = Model + Harness"** (LangChain, March 2026). Your four-layer model (stateless LLM core → Runtime → Capabilities → Safety & Scale) is sound and matches how Anthropic, OpenAI, LangChain, and Thoughtworks describe production systems, though each source slices the layers slightly differently.
- The strongest engineering consensus organizes harness components two ways that you should overlay on your diagram: (1) **by execution position** — the central agent/ReAct loop surrounded by supporting subsystems; and (2) **by control type** — Böckeler/Fowler's **guides (feedforward) vs. sensors (feedback)**, each either **computational (deterministic)** or **inferential (LLM-based)**. These two axes label nearly every component cleanly.
- Real production systems (Claude Code, OpenAI Codex, Stripe Minions, Shopify Sidekick, Anthropic's multi-agent Research) converge on the same primitives: an orchestration loop, tool/MCP layer, sandboxed execution, context/memory management with compaction, subagent orchestration, layered guardrails/permissions, and verification loops (tests + LLM-as-judge). The lesson repeated everywhere: **harness quality often matters more than model quality** — LangChain reports its coding agent "went from Top 30 to Top 5 on Terminal Bench 2.0. We only changed the harness" (deepagents-cli rose 13.7 points, 52.8%→66.5%, with the model fixed at gpt-5.2-codex).

## Key Findings

**1. Terminology is converging but not standardized.** "Agent harness," "agentic harness," "agent scaffolding," and "agentic runtime" are used largely interchangeably, but two 2026 sources draw a sharper line worth noting on your diagram. Hugging Face's May 2026 glossary separates **scaffolding** (the behavior-defining layer: instructions, tools, output format — what the model works *from*) from the **harness** (the execution runtime: the control loop, tool execution, error handling — what makes the agent *run*). LangChain and most practitioners use "harness" as the umbrella term for both. Your four-layer model treats the harness as the umbrella, which is the more common usage.

**2. The "Agent = Model + Harness" decomposition (LangChain, Vivek Trivedy, March 10, 2026)** is the cleanest top-level framing. A harness is "every piece of code, configuration, and execution logic that isn't the model itself." LangChain enumerates harness components as: System Prompts; Tools, Skills, MCPs and their descriptions; Bundled Infrastructure (filesystem, sandbox, browser); Orchestration Logic (subagent spawning, handoffs, model routing); and Hooks/Middleware for deterministic execution (compaction, continuation, lint checks).

**3. Böckeler/Fowler's guides-and-sensors taxonomy** is the field's canonical vocabulary for *classifying* components, and should be an orthogonal labeling axis on your diagram. It defines a 2×2 matrix (guide/sensor × computational/inferential).

**4. The orchestration loop is the heart of the Runtime layer**, and the dominant pattern is ReAct (Reason+Act), with plan-and-execute, reflection/self-critique, and ReWOO as variants.

**5. Context engineering and memory** is where most of the "Capabilities" layer engineering effort goes, organized around the "context rot" problem.

**6. Multi-agent orchestration** uses the orchestrator-worker pattern as the dominant production topology.

**7. Verification splits into computational vs. inferential controls.**

**8. Safety is implemented as defense-in-depth** with multiple independent layers.

## Details

### Layer 0 (Core): The Stateless LLM
The model takes in tokens (text, images, audio, video) and outputs text. Out of the box it **cannot** maintain durable state across interactions, execute code, access real-time knowledge, or set up environments (LangChain). Everything else is harness. A useful mental model from the field (Beren Millidge, cited by Daily Dose of DS): the raw LLM is "a CPU with no RAM, no disk, and no I/O" — the context window is RAM, external databases are disk, tool integrations are device drivers, and the harness is the operating system.

### Layer 1 — Runtime (orchestration loop, prompt construction, output parsing, error handling)

**The agent/orchestration loop.** The universal four-move cycle is **Perceive → Reason/Decide → Act → Observe**, repeating until a stopping condition. The model runs on the perceive/decide steps; the act phase runs your code; the observe phase reads a tool result back into context. One loop iteration is typically one LLM call + one tool call + bookkeeping. Synonyms: "agent loop," "agentic loop," "thought-action-observation cycle," "agentic execution loop." Russell & Norvig's 1995 agent definition (perceive environment via sensors, act via actuators) is the intellectual root; ReAct (Yao et al., 2022, Princeton/Google) made it practical for LLMs.

**Control-flow patterns (label these as variants of the loop):**
- **ReAct (Reason + Act)** — interleaves reasoning and action tightly; one LLM call per step; the default; grounds reasoning in real observations to reduce hallucination; gets expensive on long chains.
- **Plan-and-Execute** — one big "decide" up front produces a full plan, then a sequence of acts/observes (often with a cheaper model); fewer LLM calls, lower cost, inspectable before execution; replans on failure.
- **ReWOO (Reasoning Without Observation)** — plan once with placeholders, run tools in parallel, synthesize at the end.
- **Reflection / Reflexion / self-critique / Evaluator-Optimizer** — one model generates, another (or the same) critiques against criteria, and the loop repeats until quality is met.

A detailed, diagram-ready instantiation comes from the OpenDev terminal-agent paper (arXiv:2603.05344, Bui, March 2026), which describes an **"Extended ReAct execution loop" with six phases**: (0) **Pre-check and compaction** — drains injected messages, checks token budget, auto-compacts under memory pressure; (1) **Thinking** — optional pre-action chain-of-thought via a separate LLM call with no tool access; (2) **Self-critique** — optional self-evaluation trace separating deliberation from action; (3) **Action** — calls the LLM with full tool schemas, returning text and/or tool calls; (4) **Tool execution** — dispatches calls through the registry with approval checks (read-only tools parallel, write tools sequential); (5) **Post-processing** — decides to iterate or return, handles persistence, Stop hooks, and **doom-loop detection** (detects/breaks repetitive non-productive cycles). The loop repeats until a final text response with no tool calls, or a safety cap is hit.

**Prompt construction.** Often called the **Prompt Composer / Prompt Composition engine / dynamic system prompt construction**. Assembles the system prompt from modular sections (identity, safety policy, tool guidance/descriptions, workflow rules, dynamic runtime context, retrieved docs, memory) using priority-ordered conditional composition, mode-specific variants, provider-specific sections, and prompt caching (cacheable vs. non-cacheable segments). MindStudio notes "poor prompt construction is the single most common cause of agent failures."

**Output parsing.** Converts the model's raw output into structured tool calls / typed results; validates against schemas (e.g., Pydantic models in the OpenAI Agents SDK). Belongs in the runtime as a "sensor" in Fowler's terms (a feedback control / output validator).

**Error handling.** Retries, timeouts, malformed-output recovery, fallback model chains. The OpenDev paper describes "context-injected error recovery" (inject up to three targeted recovery messages per error sequence). Hugging Face explicitly assigns error states (retries, timeouts, malformed outputs) to the harness/runtime layer.

**Model routing / multi-model architecture.** Assigning different model roles to different LLMs. The OpenDev paper uses five model roles each with fallback chains: **Action, Thinking, Critique, Vision, and Compact** models.

### Layer 2 — Capabilities (tools, memory, context management, prompt loops)

**Tools / function calling.** Tool definitions (name, description, JSON schema of parameters), tool calling (the model emits a structured call), tool result handling (results fed back into context). Anthropic's guidance: build a few thoughtful, high-impact, consolidated tools rather than many thin ones; use **namespacing** (e.g., `asana_search`, `jira_search`) to disambiguate; carefully design the **agent-computer interface (ACI)**. Anthropic states plainly: "While building our agent for SWE-bench, we actually spent more time optimizing our tools than the overall prompt." A **Tool Registry** dispatches each call to typed handlers.

**MCP (Model Context Protocol).** Anthropic's open standard (announced November 2024), now the default way agents connect to tools; solves the "N×M integration problem" (N tools × M models → N+M). Architecture is **host → client → server** over JSON-RPC 2.0. Three server-side primitives: **Tools** (executable actions, model-controlled), **Resources** (read-only context data, application-controlled), **Prompts** (reusable templates, user-controlled). Client-side primitives: **roots, sampling** (server requests an LLM completion from the host), **elicitation**. Two transports: **stdio** (local) and **Streamable HTTP/SSE** (remote). Caveat practitioners flag: MCP servers load full tool schemas into context at connection time, consuming tokens before useful work — clients are moving to lazy-loading; CLI calls have zero schema overhead but lose centralized auth/audit.

**Skills.** Markdown capability packages (like AGENTS.md) loaded on demand via **progressive disclosure** — triggered by the user (e.g., `/review`) or by the agent when a description matches the task — to avoid front-loading context. A harness-level primitive (LangChain, Anthropic Agent Skills).

**Context engineering & the context window.** Anthropic defines context engineering as "the set of strategies for curating and maintaining the optimal set of tokens during LLM inference." The governing problem is **context rot**: as tokens increase, recall and reasoning degrade — a byproduct of transformer attention's n² token-to-token relationships, not a bug. Goal: "the smallest possible set of high-signal tokens that maximize the likelihood of your desired outcome." Anthropic's three techniques for working beyond the window:
- **Compaction** — summarize a conversation nearing the window limit and reinitialize with the summary; Claude Code preserves architectural decisions, unresolved bugs, and implementation details while discarding redundant tool outputs, then continues with the compressed context plus the most recently accessed files. (Distinguish from **summarization**: compaction strips redundant info that exists elsewhere and is more reversible; summarization is inherently lossy. "Lossiness is a spectrum, not a binary.")
- **Structured note-taking / progress logs** — persist state to external files outside the context window. Anthropic's long-running-agent harness uses a `claude-progress.txt` file plus git history; the OpenDev paper uses "tool result offloading" (keep head/tail tokens, offload full output to the filesystem).
- **Multi-agent architectures** — isolate work in subagents with clean context windows.

**Memory.** Short-term (the conversation/context window) vs. long-term (persisted across sessions). The filesystem is the foundational memory primitive (LangChain). **AGENTS.md / CLAUDE.md** files are injected into context on start as a form of continual learning. The OpenDev paper describes a **dual-memory architecture**: **episodic memory** (what happened) and **working memory** (current task state), combined into context. Retrieval/RAG is treated as a tool the agent calls on demand ("agentic RAG"), often via a multi-layer retrieval-and-assembly pipeline (anchor-based tool selection → multi-step agentic search → context assembly → context optimization).

**State / session persistence.** Conversation histories (JSON), provider caches, operation logs for rollback. The OpenAI Agents SDK calls this **Sessions** (SQLiteSession locally, SQLAlchemy/Conversations API in prod) — a persistent memory layer that auto-stores and retrieves conversation history across runs.

### Layer 3 — Safety & Scale (guardrails, verification loops, subagent orchestration, state management, tool scoping)

**Guardrails & safety.** Input guardrails (block prompt injection, off-topic, malicious input, PII) and output guardrails (filter toxic/harmful content, validate structure). In the OpenAI Agents SDK, guardrails run *in parallel* with the agent and "trip a tripwire" to short-circuit on violation; each guardrail is a separate (often cheaper) LLM call. Dedicated frameworks: NVIDIA **NeMo Guardrails** (five rail types — input, dialog, retrieval, execution, output — via Colang flow syntax), **Guardrails AI** (RAIL spec, structured-output validators), **LLM Guard** (scanning + PII anonymization). Production consensus: no single technique suffices; stack multiple layers (input validation + system-prompt hardening + output filtering + classifier models).

**Verification loops — the two control types (Böckeler/Fowler):**
- **Computational controls** — deterministic, fast, CPU-run, reliable, cheap enough to run on every change: linters, type checkers, unit/structural tests, compilers, static analysis, mutation testing.
- **Inferential controls** — semantic, LLM-based, slower, costlier, non-deterministic: **LLM-as-judge**, AI code review, semantic-duplication detection. Best run at appropriate timings (post-integration pipelines), not every commit.
Self-correction loops feed sensor output (test failures, linter messages, compiler errors, screenshots, logs) back to the agent. Fowler's key insight: design sensor messages "optimised for LLM consumption" — e.g., custom linter messages that include self-correction instructions (a positive kind of prompt injection).

**Observability / tracing.** A trace = one end-to-end agent run, composed of spans (LLM generations, tool calls, handoffs, guardrail checks). The OpenAI Agents SDK has tracing on by default. For agents, evaluate both the **final answer and the trajectory** (tool choice, tool arguments, redundant steps, recovery behavior). Production "data flywheel": traces → observability → datasets → evals → improvements → better traces. Tools: LangSmith, Langfuse, Arize Phoenix, Datadog LLM Observability, Comet Opik.

**Subagent orchestration (scale).** The dominant pattern is **orchestrator-worker** (a.k.a. lead-agent/subagent). Anthropic's multi-agent Research system: a lead agent plans, saves the plan to memory, spawns subagents in parallel — each with its own context window, tools, and exploration trajectory — which return condensed findings for synthesis (with a separate citation pass). Anthropic reports "a multi-agent system with Claude Opus 4 as the lead agent and Claude Sonnet 4 subagents outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval," at ~15× the token cost. On the BrowseComp evaluation Anthropic found "token usage by itself explains 80% of the variance" in performance (with number of tool calls and model choice as the other factors; three factors explained 95% of variance). Subagents act as compression/filtering and enforce separation of concerns. The isolation boundary is the key design decision (Anthropic's bet for research: subagents know "almost nothing" about each other). Contrast with the **swarm/peer-to-peer** model (agents share state via a message bus/scratchpad — flexible but hard to reason about). Other primitives: **routing** (a triage agent classifies and dispatches), **parallel fan-out/fan-in**, and **handoffs** (one specialist transfers control to another — a first-class OpenAI Agents SDK primitive). Anthropic's "Agent Teams" (experimental, with Opus 4.6) adds a team lead, teammates with own context windows, a shared task list, and peer-to-peer messaging.

**State management & tool scoping (permissions).** Tool scoping limits which tools each agent/subagent can call. Claude Code's permission system is a clean diagram reference: allow/ask/deny rules evaluated in **deny → ask → allow** order (first match wins, deny always precedes); enforced by the harness, *not* the model; five permission modes (default, acceptEdits, plan, dontAsk/dangerously-skip, bypassPermissions); `Task(AgentName)` rules scope which subagents can be spawned. **PreToolUse hooks** run before the permission system and can approve/deny/modify calls at runtime (exit code 2 blocks). Managed settings (`allowManagedHooksOnly`, `allowManagedMcpServersOnly`) give enterprises non-overridable governance.

**Sandboxing.** OS-level isolation as a backstop independent of model decisions. Claude Code uses macOS Seatbelt and Linux bubblewrap to restrict the Bash tool's filesystem and network access; Anthropic reports internal sandboxing reduced permission prompts by 84%. The principle (Anthropic): "even if prompt injection manipulates Claude's behavior, the sandbox can still prevent critical file modification, unauthorized network egress, and access outside defined boundaries." Permissions and sandboxing are explicitly **complementary** (permissions = first gate, sandbox = backstop).

### A diagram-ready synthesis of the two orthogonal axes
- **Axis A (execution position):** central loop (perceive-reason-act-observe / ReAct) ← surrounded by → supporting subsystems (Prompt Composition, Tool Registry, Safety System, Context Engineering, Memory/Session services, Subagent Orchestration, input/message-injection queue). This is the OpenDev paper's "ReAct loop surrounded by seven supporting subsystems."
- **Axis B (control type — Böckeler/Fowler):** every component is a **guide (feedforward)** or **sensor (feedback)**, and either **computational** or **inferential**. Guides = system prompts, AGENTS.md, skills, architecture docs, codemods, LSP/code intelligence. Sensors = linters, tests, type checkers, output parsers, review agents, LLM-as-judge, drift scans, runtime SLO monitors. The human's role is the **steering loop**: iterate the harness whenever an issue recurs.

### Real-world case studies (for diagram callouts)
- **Claude Code (Anthropic).** The Claude Agent SDK is "the agent harness that powers Claude Code." Components: agentic ReAct loop, tool system (incl. LSP-backed code intelligence), context management via compaction, memory (CLAUDE.md), hooks, skills, subagents, MCP, permission modes + sandboxing + checkpoints. For long-running tasks Anthropic uses an **initializer agent** (sets up `init.sh`, a JSON feature list of 200+ end-to-end features, initial git commit, progress file) and a **coding agent** (works one feature at a time, leaves a clean state, self-verifies via browser automation/Puppeteer MCP).
- **OpenAI Codex / "Harness engineering" (Ryan Lopopolo, Feb 11, 2026).** Built a ~1M-line internal product (~1,500 PRs) with **zero manually-written code**, ~1/10th the time. Three pillars: **context engineering** (repository knowledge base + dynamic context like observability data and Chrome DevTools browser navigation), **architectural constraints** (rigid layered architecture enforced by custom linters + structural tests + "taste invariants"), and **entropy/"garbage collection"** (background agents scan for drift and open refactoring PRs). Per-worktree bootable app + local observability stack (Victoria Logs/Metrics/Traces, queryable via LogQL/PromQL). Their conclusion: "Our most difficult challenges now center on designing environments, feedback loops, and control systems."
- **Stripe Minions.** "Over 1,300 Stripe pull requests merged each week are completely minion-produced, human-reviewed, but contain no human-written code" (up from ~1,000 two weeks prior, per Stripe's own announcement). Six-layer architecture: Slack/CLI/Web invocation → deterministic **orchestrator prefetch** (scans for links/tickets/docs via MCP, curates a surgical subset of ~15 tools from 400+) → isolated pre-warmed **devbox** (10-second spin-up, no internet/production access) → **Toolshed** central MCP server (400+ tools) → agent loop (fork of Block's Goose, interleaving LLM steps with deterministic git/lint/test code) → three-tier feedback (local lint <5s → selective CI from 3M+ tests with autofixes → max 2 CI rounds) → human review. Conditional agent rules applied per subdirectory. Lesson: "build great developer infrastructure; the agents will benefit automatically."
- **Shopify Sidekick.** Single-agent agentic loop (deliberately *not* multi-agent early). Scaled from ~20 tools to 50+ and hit "death by a thousand instructions"; solved with **Just-in-Time (JIT) instructions** (guidance delivered alongside tool data exactly when needed, preserving prompt-cache efficiency). Heavy investment in **LLM-as-judge evaluation** (multiple specialized judges, ground-truth sets, statistical correlation with human experts; "LLM judge correlation increased from 0.66 to 0.75 on average," and syntax-validation accuracy rose from ~93% to ~99% across skills) and **GRPO reinforcement-learning training** (with explicit reward-hacking mitigation). Recommendations: stay simple, tool quality over quantity, start modular, avoid multi-agent early.
- **Anthropic multi-agent Research.** Orchestrator-worker; lead agent + 3-5 parallel subagents; 90.2% over single-agent; ~15× tokens; separate citation pass.

## Recommendations

**For building the diagram, structure it as a set of concentric layers with two orthogonal labeling systems:**

1. **Keep your four-layer concentric model** (stateless LLM core → Runtime → Capabilities → Safety & Scale). It is well-supported. Place the **agent loop** spanning the Runtime layer as the "engine," with prompt construction, output parsing, error handling, and model routing as its immediate runtime services.

2. **Label every component with the guides/sensors × computational/inferential matrix** as a legend or color-coding. This is the field's canonical vocabulary and will make the diagram authoritative. Guides feed forward into the loop; sensors feed back into the self-correction path.

3. **Show the central-loop-plus-subsystems view** as an inset or alternate view: ReAct loop (6 phases) surrounded by the supporting subsystems (Prompt Composition, Tool Registry, Safety System, Context Engineering, Memory/Session, Subagent Orchestration, input queue). This is the most diagram-ready primary-source decomposition available.

4. **For the tool layer**, show three nested concepts: tool *definitions* → MCP (host/client/server, three primitives) → sandboxed *execution* → tool *scoping/permissions* (deny→ask→allow). Note the MCP context-cost caveat.

5. **For Safety & Scale, draw defense-in-depth as stacked independent layers** (the OpenDev five-layer model is ideal): Prompt-Level Guardrails → Schema-Level Tool Restrictions → Runtime Approval System → Tool-Level Validation → Lifecycle Hooks, with OS sandboxing as the outermost backstop.

6. **Note terminology disagreements explicitly** in a footnote: (a) scaffolding vs. harness (Hugging Face's distinction vs. LangChain's umbrella usage); (b) whether memory/context management sits in "Capabilities" or is its own layer; (c) Paul Iusztin's alternative 8-component model (orchestration, execution, state management, tool interface, monitoring, feedback, strategy, memory layers) vs. blog-synthesized 5-layer models.

**Benchmarks/thresholds that would change the design:** If your target is a *coding* agent, weight verification (computational sensors + CI loops) and context persistence heavily — this is where Codex/Stripe/Claude Code invest most. If your target is a *research/breadth* agent, weight subagent orchestration and context isolation (Anthropic Research). If a *customer-facing conversational* agent, weight input/output guardrails and human-in-the-loop approval over multi-agent complexity (Shopify's explicit advice). If single-agent performance is adequate, **do not** add multi-agent orchestration — it adds ~15× token cost and coordination complexity.

## Caveats
- **Recency and source quality:** The core architectural claims are drawn from primary engineering sources (Anthropic, OpenAI, LangChain, Stripe, Shopify, Martin Fowler/Thoughtworks, the MCP spec). Many *synthesis* articles (Medium, DEV, vendor blogs) repeat these primaries; where only secondary sources existed I have attributed accordingly.
- **"X-layer" model proliferation:** The harness-engineering-ai.com "five-layer" model and several other "X-layer" framings are vendor/blog syntheses, not standardized; treat specific layer counts as one author's organization, not an industry standard. The OpenDev paper's four top-level layers (Entry & UI, Agent, Tool & Context, Persistence) and five-layer safety stack are from a single descriptive technical report — well-structured, but one team's implementation.
- **Forward-looking framing:** LangChain, Fowler, and OpenAI all note the harness is the layer "most tightly coupled to the model's current capabilities" and that some harness functions (planning, self-verification, long-horizon coherence) will be **absorbed into models** over time — so any diagram is a snapshot of mid-2026 practice, not a permanent architecture.
- **Metaphor limits:** Böckeler explicitly flags that "harness within a harness" stretches the metaphor (inner/builder harness vs. outer/user harness); the concentric-circle depiction is a useful convenience, not a literal containment.
- **Numbers to treat carefully:** The "88% of agent projects fail" and "70% of performance lives outside the model" figures come from vendor marketing content (Miraflow, Medium) and should be presented as claims, not established facts. The 90.2% multi-agent improvement, 15× token figure, and 80%-of-variance claim are from Anthropic's own engineering blog (primary, but self-reported on internal evals). The Terminal-Bench 2.0 Top-30→Top-5 / 52.8%→66.5% jump and the Stripe and Shopify figures are likewise self-reported by those organizations.
