# The Single-Loop Agent: A Conceptual Architecture Guide

*A provider-neutral, TypeScript-oriented design document for a general-purpose AI assistant built around one agentic loop. No code — concepts, interfaces-in-prose, and design heuristics only.*

## TL;DR

- **Build one loop, not a framework.** Every capability your assistant needs — subagents, orchestration, skills, tools, and MCP — collapses into a single primitive: "the model calls tools in a loop until it stops." Subagents are just a recursive invocation of that same loop with a fresh context window, exposed to the model as one more tool. Anthropic, Cognition, and the Vercel AI SDK have all converged on this same six-lines-of-logic pattern; the sophistication lives at the edges (tool design and context engineering), not in the loop.
- **Context is your scarcest resource, and context isolation is your primary scaling mechanism.** Treat the context window as a finite attention budget subject to "context rot." The single most powerful architectural lever is spawning a subagent with its own isolated context that does expensive exploration and returns only a distilled summary. Skills, lazy tool loading, and on-demand MCP all exist to keep the main context lean.
- **Default to a single agent; escalate to multi-agent only when the task is parallelizable, high-value, and exceeds one context window.** Multi-agent systems use about 15× the tokens of a chat and introduce coordination failure modes. Use them for breadth-first research, not for tightly-coupled work like most coding. When in doubt, one loop with good tools beats an orchestra.

## Key Findings

1. **The canonical agent is an LLM, a loop, and tools.** The loop gathers context, calls the model, executes any requested tool calls, appends the results as messages, and repeats until the model emits no tool calls or a stop condition trips. This is the entire architecture; everything else is a variation on what goes into the context and what tools are available.

2. **"Everything is a tool" is the unifying abstraction.** In production agents like Claude Code, spawning a subagent is itself a tool call (the "Task"/dispatch_agent tool). The loop only knows how to call tools; therefore subagents, skill invocation, file operations, and MCP servers all present through one uniform tool interface. This keeps the core single-threaded and comprehensible.

3. **Subagents provide context isolation, the key to scaling.** A subagent runs the same loop with a clean context window, explores using tens of thousands of tokens, and returns a compressed 1,000–2,000 token summary. The detailed exploration never pollutes the parent's context. Anthropic's multi-agent research system, built on this pattern, "outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval" — but multi-agent systems "use about 15× more tokens than chats" (single agents ~4×).

4. **Skills and tools are different things.** A tool is an action the model can invoke (a function with a schema). A skill is on-demand *knowledge/procedure* — a folder with a SKILL.md file whose metadata is always visible but whose full body loads only when relevant (progressive disclosure). Skills teach the agent *how* to do something; tools let it *do* something.

5. **MCP should be lazy.** Loading every MCP tool definition upfront is expensive — Anthropic cites a five-server setup as "58 tools consuming approximately 55K tokens before the conversation even starts" (and internally has "seen tool definitions consume 134K tokens before optimization"). Treat MCP as just another tool source behind your uniform tool interface, connect on demand, and discover tools dynamically rather than eagerly.

6. **The industry disagrees productively about multi-agent.** Cognition ("Don't Build Multi-Agents") warns that parallel writers make conflicting implicit decisions; Anthropic shows multi-agent excelling at parallel research. Both are right: the deciding factor is whether the work is truly parallelizable with independent sub-contexts and whether writes stay single-threaded.

## Details

### 1. Philosophy: One Loop, Everything Is a Tool

Start from a deliberately austere premise. An agent is a large language model that autonomously uses tools in a loop. That is the definition Anthropic settled on, and it is worth taking literally as an architectural constraint rather than a slogan. Every framework examined in public reverse-engineering efforts — Claude Code, Codex, Cursor, the Vercel AI SDK, LangGraph, smolagents, the OpenAI Agents SDK — converges on the same core: a while-loop that calls an LLM, checks whether the response contains tool calls, executes them if present, and stops if not. The differences between them are costumes over identical logic.

The design payoff of committing to this is enormous. If you resist the temptation to build special-purpose subsystems (a "research engine," an "orchestration engine," a "skills engine") and instead force every capability to express itself as *either a message in the context or a tool the model can call*, you get a system that is small, debuggable, and durable across model upgrades. This is the "bitter lesson" applied to agent design: keep the scaffolding thin, because as models improve they need less of it, and hard-coded cleverness becomes dead weight. Anthropic makes the same point when they note their harness is "designed to shrink" — as models get smarter, hand-written planning steps get deleted.

Concretely, the unifying abstraction is: **subagents, skills, and MCP are not first-class architectural citizens; they are things the model reaches for through the one tool-calling channel.** Spawning a subagent is a tool call. Loading a skill body is (conceptually) reading a file, which is a tool call. Invoking an MCP server's capability is a tool call. Your loop does not need to know the difference. This is exactly how Claude Code works: sub-agents are invoked through a Task/dispatch_agent tool, and their results "feed back into the main loop as regular tool outputs, maintaining the single-thread simplicity of the overall system."

### 2. The Anatomy of the Single Loop

Think of the loop as a turn-based state machine over a single growing conversation transcript. One iteration ("turn" or "step") consists of four conceptual phases:

**Phase A — Gather/curate context.** Assemble the array of messages to send to the model: the system prompt, the available tool schemas (or a lightweight index of them — see §5 and §6), any always-loaded instructions, retrieved just-in-time data, and the running message history. This assembly step is not passive plumbing; it is where context engineering happens on every single turn. Anthropic frames this precisely: "in contrast to the discrete task of writing a prompt, context engineering is iterative and the curation phase happens each time we decide what to pass to the model."

**Phase B — Call the model.** Send the assembled context to the LLM through your provider adapter (see §9). The response is either a final text answer, or one or more tool-call requests (name + arguments), or a mix. Streaming is a presentation concern layered on top; the loop's logic keys off the structured tool-call requests.

**Phase C — Execute tools and append results.** For each tool call the model requested, dispatch it through the tool registry, capture the result (or error), and append it to the transcript as a tool-result message keyed to that call's ID. If the model requested multiple independent tools, execute them concurrently (fan-out) and collect the results.

**Phase D — Check termination, then repeat.** If the model produced a final answer with no pending tool calls, stop. Otherwise loop back to Phase A with the enlarged transcript.

**Termination and safety rails.** A robust loop never trusts the model to stop on its own. Enforce, at minimum: a maximum-iterations counter (a hard ceiling on turns); a token/cost budget for the whole run and per subagent; a wall-clock timeout; and detection of degenerate cycles (e.g., the same tool called with the same arguments repeatedly, or oscillation between two states). Any of these tripping should end the loop gracefully with a partial result and a clear reason, not a crash. These are the "deterministic safeguards" — retry logic, budgets, checkpoints — that Anthropic pairs with the model's own adaptability. The Vercel AI SDK expresses the same idea with its `stopWhen`/`stepCountIs` stop conditions (a default of about 20 steps), and the OpenAI Agents SDK wraps its `while(true)` in guardrails that run at input, output, and tool boundaries as filters on the loop rather than part of it.

### 3. Subagents and Context Isolation

**A subagent is a recursive call to the same loop with a fresh context.** This is the single most important conceptual move in the whole design. When the main agent decides a piece of work deserves its own context, it calls a "spawn subagent" tool. Your harness handles that tool call by instantiating the *same loop* with: a brand-new, empty message history; a task description authored by the parent; possibly a narrowed tool set and a smaller model; and its own budget/turn ceiling. The subagent runs to completion, produces a result, and that result is handed back to the parent as the tool-call's return value. From the parent loop's perspective, nothing special happened — it called a tool and got a string back.

**Why isolation is the point.** "The essence of search is compression: distilling insights from a vast corpus." A subagent can read ten documents, run twenty searches, and burn 50K tokens of exploration, then return a 1,500-token synthesis. The parent's context grows by only 1,500 tokens, not 50K. This is what lets the overall system handle problems far larger than any single 200K-token window. Anthropic describes exactly this: "Each subagent might explore extensively, using tens of thousands of tokens or more, but returns only a condensed, distilled summary of its work (often 1,000–2,000 tokens)."

**What should and shouldn't cross the parent/child boundary.**
- *Down (parent → child):* a crisp, self-contained task specification. Anthropic learned this the hard way — vague instructions like "research the semiconductor shortage" caused subagents to duplicate each other's work or misinterpret scope. Each subagent needs an explicit objective, an output format, guidance on which tools/sources to use, and clear task boundaries. Give the child *what it needs to do its job*, not the parent's entire transcript.
- *Up (child → parent):* only the distilled result. Raw tool outputs, intermediate reasoning, and dead-end explorations should stay locked inside the child's context and be discarded when it terminates. This is the anti-pollution firewall.
- *The tension with Cognition's advice:* Cognition argues (Principle 1) "Share context, and share full agent traces, not just individual messages," and (Principle 2) "Actions carry implicit decisions, and conflicting decisions carry bad results." This is not a contradiction of the isolation pattern — it is a warning about *when* isolation is dangerous. When subagents make interdependent decisions (e.g., two agents writing code that must fit together), starving them of shared context produces conflicting choices. Isolation is safe for *read-heavy, independent* subtasks (research, search, analysis) and dangerous for *coupled, write-heavy* ones. Cognition considers these two principles "so critical, and so rarely worth violating, that you should by default rule out any agent architectures that don't abide by them."

**Preventing context pollution and runaway recursion.**
- Cap recursion depth. Historically Claude Code forbade subagents from spawning their own subagents (one level of delegation) specifically to prevent "recursive explosion"; it has since allowed limited nesting, but the principle stands: bound the depth explicitly.
- Consider the file system as a side channel. Anthropic's "output to a filesystem" pattern has subagents write large artifacts (code, reports) to disk and pass back only a lightweight reference, avoiding the "game of telephone" where copying big outputs through conversation history loses fidelity and burns tokens.
- Budget every child. A subagent with no turn/token ceiling is an unbounded liability.

### 4. Orchestration Patterns

Once subagents exist, orchestration is just *how the parent decides to use them.* The main loop is the orchestrator. The canonical patterns:

- **Orchestrator–workers.** A lead agent analyzes the request, forms a plan, and spawns specialized workers for pieces of it, then synthesizes their results. This is the pattern behind Anthropic's research system (a LeadResearcher spawning subagents) and is ideal when the subtasks aren't known in advance and must be determined dynamically from the input.
- **Routing.** A classifier (often a cheap model call) inspects the input and directs it to the right handler or specialist. Routing decisions are cheap (tens of milliseconds) relative to the work they gate.
- **Parallel fan-out / fan-in.** Spawn several independent subagents concurrently and gather their results. Anthropic cut research time by up to 90% for complex queries this way: the lead spins up 3–5 subagents in parallel, and each uses tools in parallel. Best when subtasks are genuinely independent.
- **Sequential pipeline.** Chain steps where each depends on the previous output (e.g., outline → draft → critique). Use when the order is fixed and dependencies are strict.
- **Evaluator–optimizer.** One agent produces, another critiques, and they iterate. Cognition reports that a coding agent and a review agent work *best when they do not share context beforehand*, because putting the same model in two roles with independent context produces genuinely uncorrelated critique.

**The core decision: spawn a subagent, or handle it inline?** This is the judgment your orchestrator prompt must encode. Spawn a subagent when several of these hold:
- **Context budget:** the subtask will generate a lot of intermediate tokens (extensive search, large file reads) that you don't want polluting the main context. Isolation pays for itself.
- **Task independence:** the subtask can be specified crisply and completed without ongoing back-and-forth with the parent or sibling agents.
- **Parallelism:** there are multiple such independent subtasks that can run concurrently for a latency win.
- **Risk isolation:** the subtask is exploratory or failure-prone and you want its blast radius contained.
- **Distinct configuration:** the subtask wants a different tool set, model, or system prompt.

Handle it inline (no subagent) when: the task is small and cheap; it needs the full shared context to make coherent decisions; it involves tightly-coupled writes; or the coordination overhead exceeds the work. Remember the fixed cost: each subagent re-pays for its own context setup (community estimates put the overhead around 20K tokens per Claude Code Task/subagent), so spawning one to do trivial work is pure waste. Anthropic embeds explicit scaling heuristics in its lead-agent prompt: simple fact-finding gets 1 agent and 3–10 tool calls; comparisons get 2–4 subagents; only genuinely complex research warrants 10+ subagents. Early versions that lacked these rules spawned 50 subagents for simple queries.

### 5. Skills: On-Demand Procedural Knowledge

**What a skill is.** A skill is a folder containing a SKILL.md file — YAML frontmatter (a `name` and a `description`) plus a Markdown body of instructions, optionally accompanied by `scripts/`, `references/`, and `assets/` subfolders. It packages *procedural knowledge*: how to fill out a PDF form, how your team formats a weekly report, the steps of a data-analysis pipeline. Originally created by Anthropic and released as an open standard (agentskills.io), the format has been adopted across many agent products.

**Progressive disclosure is the whole idea.** Skills load in three tiers, and this is what makes them scale:
1. *Discovery:* at startup, only each skill's name and description load into the system prompt (~30–50 tokens each). The agent knows the skill *exists* and *when it's relevant* without paying for its contents. All 17 skills in Anthropic's reference repository together cost only around 1,700 tokens at this tier — less than a single activated skill.
2. *Activation:* when the model judges a skill relevant to the task, it loads the full SKILL.md body into context (Anthropic's guideline: keep this under ~500 lines / ~5K tokens).
3. *Execution:* referenced files (`reference.md`, `forms.md`) and scripts load only if and when a step actually needs them; scripts can run without their source ever entering context.

**How skills differ from tools — the crucial conceptual distinction.** A tool is a *capability* the model invokes by emitting a structured call; it changes what the agent *can do*. A skill is *context* the model reads; it changes what the agent *knows*. A tool executes; a skill instructs. A tool's schema must always be present (or discoverable) for the model to call it; a skill's body is inert text pulled in on demand. In practice they compose: a skill's instructions frequently tell the agent which tools to use and in what order. If you already have a filesystem-read tool, "loading a skill" is literally just the model choosing to read a SKILL.md file — reinforcing the "everything is a tool" thesis. Skills also differ from a bloated system prompt precisely because of progressive disclosure: they keep the bulk of their content on disk until needed, rather than permanently occupying the attention budget. (Anthropic frames the context window as a public good and skills as being "intentional about what information goes into the context window and what stays on disk until it's actually needed.")

### 6. Tools: Registry, Schemas, Dispatch, and Safety

**The tool registry.** Conceptually, a registry is a lookup table from tool name to a record containing: a human/model-readable description, an input schema (parameters, types, which are required, descriptions of each), an output shape, an executor (the function that actually runs), and metadata for gating (risk level, permissions required, whether it mutates state). Your loop consults the registry in two moments: when assembling context (to expose schemas or an index to the model) and when dispatching a call (to find and run the executor).

**Schema design.** The schema is the contract between the model and your code, so treat it like an API you're designing for a somewhat literal-minded consumer. Anthropic's guidance: build a few thoughtful, high-impact tools rather than many overlapping ones; consolidate multi-step operations (a `schedule_event` tool that finds availability *and* books, rather than separate `list`/`create` tools); return token-efficient results (a `search_logs` that returns only relevant lines, not a `read_logs` that dumps everything). Descriptions and parameter names must be unambiguous — "if a human engineer can't definitively say which tool should be used in a given situation, an AI agent can't be expected to do better."

**Deferred/lazy tool loading and tool search.** When your catalog grows past a few dozen tools, exposing every schema on every turn wastes context and *degrades* selection accuracy — with too many options the model picks wrong tools, hallucinates parameters, and loses focus. The fix mirrors skills' progressive disclosure: present a lightweight index (names + one-line descriptions), and provide a *tool-search meta-tool* the model calls to pull in the full schema of a specific tool only when it decides to use it. Anthropic shipped exactly this as the "Tool Search Tool," reporting that "this represents an 85% reduction in token usage while maintaining access to your full tool library," alongside meaningful accuracy gains on large tool libraries (Opus 4 improved from 49% to 74%, and Opus 4.5 from 79.5% to 88.1% on their MCP evaluations with the feature enabled). Newly loaded tools are naturally picked up on the next loop iteration.

**Dispatch, errors, and retries.** When the model requests a tool, the loop: validates the arguments against the schema (reject/repair malformed calls before executing); runs the executor, ideally with a timeout; and appends a result message. Errors should be returned *to the model as tool results*, not thrown as exceptions that kill the loop — Anthropic found that "letting the agent know when a tool is failing and letting it adapt works surprisingly well." Distinguish transient failures (network blips → automatic retry with backoff, handled by the harness) from semantic failures (bad arguments → return the error text so the model can correct itself). Wrap each tool execution as an independently retriable, checkpointed step so a failing tool re-runs without re-running the whole turn.

**Safety and permission gating.** Every tool call should pass through a permission gate before execution. The gate answers "whether"; sandboxing answers "where." A practical design: an allow-list of always-permitted patterns (safe reads, known-good build steps run unattended), a deny-list enforced at the infrastructure level (so the agent cannot invoke a forbidden tool even if it reasons toward one), and everything else prompting a human for inline approval. Claude Code requires explicit allow/deny decisions for write operations, risky shell commands, and external (MCP/web) tool use. Pair this with a full audit trail — timestamps, model/prompt versions, the arguments, the permission decision — and a "dry-run" mode for risky calls. Give risky tool execution OS-level isolation (containers, restricted syscalls, resource limits).

### 7. MCP: Connect and Discover Only When Needed

**Treat MCP as just another tool source.** The Model Context Protocol is an open standard (introduced by Anthropic in November 2024) for connecting agents to external systems; a server advertises tools, and thousands now exist. Architecturally, an MCP tool should be *indistinguishable from a native tool* once it's behind your uniform tool interface. Your registry adapts each MCP server's advertised tools into the same record shape (name, schema, executor-that-calls-the-server) your loop already understands. The loop never learns the acronym "MCP."

**The cost problem, quantified.** Naively, most MCP clients load *all* tool definitions from *all* connected servers upfront, into context, on every turn. This does not scale: real-world reports include a single Docker MCP setup consuming ~126K tokens across 135 tools, and GitHub's server alone eating roughly a quarter of a 200K window. Anthropic's own example: a five-server configuration is "58 tools consuming approximately 55K tokens before the conversation even starts," and internally they have "seen tool definitions consume 134K tokens before optimization." A second, subtler cost: chaining MCP tools passes each intermediate result back through the model's context (a document fetched from one server and written to another is paid for twice).

**Lazy connection and dynamic discovery.** The remedies, all consistent with the single-loop philosophy:
- *Lazy connection:* don't connect to a server until the agent actually needs it. Keep servers deferred; connect (and only then fetch their tool list) on first use.
- *Dynamic discovery:* expose a short catalog of server/tool names and one-line summaries; load a specific tool's full schema only when the agent commits to using it — the same metadata-first pattern as skills and tool search.
- *Code execution with MCP:* rather than round-tripping every intermediate result through the model, present MCP servers as code modules the agent calls from a sandboxed execution environment, keeping large payloads out of context. Anthropic reports that for a Google-Drive-to-Salesforce transcript-move workflow, "this reduces the token usage from 150,000 tokens to 2,000 tokens—a time and cost saving of 98.7%," and a related "Programmatic Tool Calling" feature (which lets the model orchestrate tools through code rather than one API round-trip at a time) cut average usage on complex research tasks from 43,588 to 27,297 tokens, a 37% reduction. The tradeoff: running model-generated code demands a secure sandbox, resource limits, and monitoring — real operational overhead that direct tool calls avoid.

**When to load many MCP tools eagerly anyway.** If a small set of tools is used in nearly every session, the discovery round-trip is pure latency; pin those upfront. The rule is contextual: eager for the always-used few, lazy for the long tail.

### 8. Context Engineering as the Cross-Cutting Discipline

Everything above is ultimately in service of one scarce resource. Context is finite not merely because windows have a token cap but because of *context rot*: as the token count rises, the model's ability to accurately recall and reason over any given fact declines. This stems from the transformer's architecture (n² pairwise attention over n tokens) and from training distributions weighted toward shorter sequences. The practical mandate: **find the smallest set of high-signal tokens that maximizes the likelihood of the desired outcome.** Every token spent has a marginal cost to the model's "attention budget."

Anthropic's three techniques for long-horizon work, each mapping to a design decision:
- **Compaction:** when the transcript nears the window limit, summarize it and reinitialize a fresh window with the summary plus the few most-recently-touched artifacts. Preserve architectural decisions, unresolved bugs, and key implementation details; discard redundant tool outputs. The lightest-touch form is *tool-result clearing* — once a tool result is deep in history, the raw payload rarely needs to persist. (Note the operational caution surfaced in reverse-engineering of Claude Code: robust systems set a circuit-breaker, e.g., stop attempting compaction after several consecutive failures rather than looping forever.)
- **Structured note-taking (agentic memory):** the agent writes notes to a file outside the context (a NOTES.md, a to-do list, a research plan) and reads them back later. This is how an agent maintains coherence across context resets — famously, an agent playing Pokémon kept accurate tallies across thousands of steps this way. Critically for long research, persisting the *plan* to memory means a context truncation doesn't lose the strategy.
- **Sub-agent architectures:** covered in §3 — the strongest lever, isolating detailed context in children so the parent only ever holds distilled summaries.

Pair these with **just-in-time retrieval**: rather than pre-loading all possibly-relevant data, hold lightweight identifiers (file paths, links, queries) and load the actual content on demand via tools. File names, folder structure, and timestamps are themselves signal. Claude Code uses a hybrid — drop a CLAUDE.md into context upfront, but use glob/grep to pull files just-in-time. **What to persist in files vs. context:** durable state, large artifacts, and anything needed across sessions go to the filesystem; only the currently-relevant working set lives in context.

### 9. Provider Neutrality: A Thin Adapter Layer

To stay vendor-agnostic, isolate everything provider-specific behind a narrow adapter interface and let the loop speak only in your own neutral vocabulary. The adapter's job is translation, and it should be *thin* — the more logic it holds, the less portable you are.

**What the adapter normalizes:**
- *A unified message format.* Internally, represent a conversation as an ordered list of messages with roles (system, user, assistant, tool) and typed content parts (text, tool-call, tool-result, and possibly image/file). Every provider's idiosyncratic request/response shape maps to and from this. The Vercel AI SDK's "message-parts" model and its uniform `generateText`/`streamText` surface are a good reference: a single call shape works identically across 25+ providers (OpenAI, Anthropic, Google, Bedrock, Azure, xAI, Mistral, and more), so switching models is "changing two lines of code."
- *A unified tool-call representation.* Providers differ in how they express function calling; your adapter maps all of them to a single "the model requested tool X with arguments Y, tracked by call-id Z" structure and maps your tool-result back into whatever shape the provider expects.
- *Streaming.* Normalize each provider's event stream into one internal stream of typed deltas (text chunks, tool-call fragments, completion signals) so your loop and UI consume one format regardless of source.
- *Token accounting and cost.* Normalize usage reporting (input/output/cached tokens) so budget enforcement (§2) works uniformly, and so you can attribute cost per subagent.
- *Capability flags.* Surface differences (does this model support parallel tool calls? extended thinking? a memory tool?) as capability metadata the loop can branch on, rather than hard-coding vendor assumptions.

Existing neutral abstractions to study as design references (not necessarily to adopt wholesale): the Vercel AI SDK (unified provider API, tool-loop agent abstraction, `prepareStep` for per-step control of model/tools/messages/system-prompt), and OpenRouter-style unified gateways that expose many providers behind one API shape. The lesson from all of them: the loop, the registry, and the context logic should have *no idea* which vendor is behind the adapter.

### 10. State Management, Checkpointing, and Resumability

**Conversation history is the core state.** The single source of truth for a run is the ordered message transcript (system/user/assistant/tool messages, with tool results as first-class messages keyed to their call IDs). Almost everything else — which tools are available, the current budget, subagent handles — is derived or auxiliary. Designing state this way keeps the system inspectable: you can render, diff, and replay a run from its transcript.

**Statefulness makes errors compound, so checkpoint.** Agents run for many turns maintaining state; "without effective mitigations, minor system failures can be catastrophic." Restarting from scratch is expensive and infuriating to users. The remedy is durable, resumable execution: persist the transcript (and any external memory files) at checkpoints — practically, after each turn and after each tool result — so that a crash or a rate-limit resumes from the last good state rather than the beginning. Frameworks like Inngest and Temporal formalize this by wrapping each model call and each tool execution as an independently retriable, checkpointed step; the conceptual takeaway is provider-independent. For deploys of long-running agents, Anthropic uses "rainbow deployments" (gradually shifting traffic while both versions run) so that updates don't break agents mid-run.

### 11. Failure Modes, Anti-Patterns, and When NOT to Go Multi-Agent

**Loop-level failure modes:**
- *Infinite / degenerate loops:* the model never stops, or oscillates. Mitigation: hard iteration caps, budget limits, and repetition detection (§2).
- *Context explosion:* the transcript grows until quality collapses under context rot. Mitigation: compaction, tool-result clearing, subagent isolation (§8).
- *Subagent result bloat:* subagents return verbose dumps instead of distilled summaries, defeating the purpose of isolation. Mitigation: enforce output formats and token ceilings on child returns; use filesystem artifacts for big outputs (§3).

**Orchestration anti-patterns:**
- *Over-orchestration:* deploying a committee of agents where one loop with good tools would do. This is the most common and most expensive mistake. Multi-agent systems use about 15× the tokens of a chat, so they must be reserved for tasks whose value justifies the spend.
- *Tool sprawl:* dozens of overlapping, vaguely-scoped tools that confuse tool selection and consume context. Mitigation: curate a minimal, non-overlapping set; namespace related tools by service and resource (e.g., `asana_search`, `jira_search`); lazy-load the long tail (§6).
- *Naive parallel writers:* the Cognition critique — parallel agents making conflicting implicit decisions about style, edge cases, and structure, producing fragile, incoherent output because they lack shared context.

**When NOT to build multi-agent (the decisive guidance).** Default to a single loop. Cognition's position is that most teams should not build multi-agent systems, because the two hardest principles — sharing full context/traces, and avoiding conflicting implicit decisions — are so rarely worth violating that you should "by default rule out any agent architectures that don't abide by them." Anthropic's own framing agrees on the boundary: multi-agent excels only at "valuable tasks that involve heavy parallelization, information that exceeds single context windows, and interfacing with numerous complex tools," and is a *poor* fit for domains requiring shared context or dense inter-agent dependencies — "most coding tasks involve fewer truly parallelizable tasks than research." A secondary industry write-up (Beam AI, 2026) attributes to Princeton NLP the finding that "a single agent matched or outperformed multi-agent systems on 64% of benchmarked tasks when given the same tools and context," with multi-agent "adding 2.1 percentage points of accuracy at roughly double the cost" — a useful directional signal, though we could not locate the primary Princeton source to verify it. The synthesis: reach for multi-agent when the task is (a) high-value, (b) genuinely parallelizable into independent read-heavy subtasks, and (c) larger than one context window — and keep writes single-threaded. Otherwise, one loop with excellent tools and disciplined context engineering wins.

## Recommendations

**Stage 1 — Build the spine (before any advanced feature).** Implement the four-phase loop (§2) with a provider adapter (§9) and a message-based state model (§10) first. Wire in hard termination controls — max iterations, token/cost budget, timeout, repetition detection — from day one; they are not an afterthought. Add a minimal tool registry (§6) with 3–5 well-designed, non-overlapping tools and per-call permission gating. *Benchmark to advance:* the loop reliably completes multi-tool tasks, always terminates, and never lets an error crash the run. Do not build subagents or MCP until this is solid.

**Stage 2 — Add context isolation via subagents.** Introduce the "spawn subagent" tool as a recursive invocation of the same loop with a fresh context, a bounded budget, and a required output format (§3). Encode the spawn-vs-inline heuristics (§4) and scale-to-complexity rules (1 agent for fact-finding, 2–4 for comparisons, 10+ only for complex research) into the orchestrator's system prompt. Cap recursion depth. *Benchmark to advance:* on a task that exceeds one context window, the subagent version completes it with materially lower peak main-context usage than a single agent — this proves isolation is working.

**Stage 3 — Add skills and lazy tool/MCP loading, in that order.** Implement progressive disclosure for skills (metadata always in prompt, body on demand) (§5). Once your tool count exceeds ~20–30, add a tool-search meta-tool and switch the long tail to lazy loading (§6). Treat MCP as a tool source behind the uniform interface with lazy connection and dynamic discovery (§7); pin only the always-used servers eagerly. *Benchmark to advance:* startup context stays roughly flat as you add skills and MCP servers — if adding a server inflates every turn's token count, discovery isn't lazy.

**Stage 4 — Harden for long-horizon and production.** Add compaction with a circuit-breaker, structured note-taking to files, and checkpoint-based resumability (§8, §10). Add full tracing (decision patterns, tool outcomes, per-subagent cost) — Anthropic found production tracing essential to debugging non-deterministic agents. Start evaluations early with ~20 real queries and an LLM-as-judge rubric; you do not need hundreds of cases to see large effects.

**Thresholds that should change your decisions:**
- If token cost per successful task is dominated by *tool definitions* rather than reasoning, prioritize lazy tool loading / code-execution-with-MCP before anything else.
- If subagents return more than ~2K tokens on average, tighten their output contracts or route large outputs to the filesystem.
- If you observe conflicting or incoherent output from parallel workers, collapse them into a single loop or a sequential pipeline with shared context — you have hit the Cognition boundary.
- If a task is not parallelizable, not high-value, or fits in one window, do not use multi-agent at all.

## Caveats

- **The field is young and moving monthly.** Specifics — Claude Code's recursion depth, which clients support lazy MCP loading, exact token thresholds — change frequently. Several figures here (e.g., the ~20K-token per-subagent overhead, Claude Code's internal `nO`/`I2A` module names, five-level nesting, the file-based mailbox for parallel agents) come from community reverse-engineering of obfuscated code, not official documentation, and should be treated as directional rather than authoritative. Treat all such numbers as "verify in your version."
- **The multi-agent debate is genuinely unsettled.** Cognition and Anthropic published nearly opposite-sounding guidance within a day of each other; both are experienced teams describing different workloads (coupled coding vs. parallel research). Notably, Cognition later reported deploying multi-agent patterns that *do* work — but only the narrow class where multiple agents contribute intelligence while writes stay single-threaded. Don't treat either headline as universal law; the workload determines the answer.
- **Token-reduction and performance figures are vendor-reported and workload-specific.** The 90.2% multi-agent improvement, the 98.7% and 85% token reductions, the 37% Programmatic-Tool-Calling reduction, and the "15× tokens" figure are all from Anthropic's own posts on their own evals and examples. The Princeton "64% / 2.1 points" figure is from a secondary blog citing an unverified primary source. These demonstrate the *shape* of the tradeoffs, not guarantees you will reproduce; the underlying point (isolation and lazy loading save context; multi-agent costs far more) is robust even if your exact numbers differ.
- **"Everything is a tool" is a simplifying lens, not a law.** Some concerns (streaming UI, permission prompts, checkpointing, deployment) genuinely live outside the loop as cross-cutting infrastructure. The abstraction is valuable because it keeps the *core* small, but a production system still needs real engineering at the edges — which, as Thorsten Ball and Anthropic both note, is where most of the actual work ("the last mile") turns out to be.
- **Provider neutrality has a cost.** A thin adapter cannot always expose a vendor's most advanced, non-standard capabilities (specialized prompt caching, bespoke thinking modes, provider-specific memory tools). Design the adapter to surface these as optional capability flags the loop can exploit when present and degrade gracefully when absent, rather than pretending all providers are identical.
